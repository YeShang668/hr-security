# 第 7 周 Bug 与踩坑记录（审计日志 AOP + KEK/DEK 密钥管理）

> 记录规则：只记"当时现象 → 定位过程 → 根因 → 修复 → 沉淀成什么规矩"，
> 方便以后回看时能复用判断，而不是只看到一个结论。

## BUG7-1（重要）：LIKE 谓词的占位符与参数个数不匹配，接口直接 500

**现象**：轮换密钥后第一次调 `POST /api/admin/keys/k1/disable`，以及重加密接口，
都返回 500 `系统繁忙，请稍后重试`，但 rotate 接口本身是好的。

**定位过程**：

1. 看应用日志，异常是 `BadSqlGrammarException: bad SQL grammar [SELECT COUNT(*) FROM sys_employee
   WHERE ((phone_enc LIKE ? OR id_card_enc LIKE ? OR bank_card_enc LIKE ? OR salary_enc LIKE ?))]`；
2. SQL 看着完全合法，第一反应是"表名列名写错了？"——但列名是从常量拼的，没有拼错；
3. 数一下问号：一行 4 个 `?`（4 个敏感列），而我传的参数只有 1 个（一个前缀字符串）——
   **Spring 报的 "bad SQL grammar" 实际是"参数个数与占位符个数不一致"**，
   它的提示信息很容易把人往"SQL 语法"上带偏。

**根因**：`singlePredicate(keyId)` 为**每一个敏感列**都生成一个 `?`（4 个），
但参数列表按"每个 keyId 一个前缀"构造（1 个）。二者必须逐列对齐。

**修复**：新增 `prefixArgs(keyIds)` 与谓词生成逻辑一一对应——同一个前缀按列数重复 4 次，
并在方法注释里把这个坑写清楚（见 `DataKeyServiceImpl#prefixArgs`）。

**沉淀的规矩**：

- **动态拼 SQL 时，"生成谓词"和"生成参数"必须是同一个函数的两半**（或干脆一起返回），
  分成两处写早晚会漂移；
- 看到 `BadSqlGrammarException` 但 SQL 本身没毛病时，**先数问号**，再怀疑语法；
- 测试用例 `keyrotation-e2e-test.sh` 的 K11/K12 恰好覆盖这两个接口，
  它们第一次跑就抓到了这个 bug（说明"轮换必须端到端跑一遍"这条测试设计是对的——
  单测只测 rotate 是发现不了的）。

## BUG7-2（测试设计问题）：用一个已被踢下线的 token 去测"403 权限"

**现象**：`audit-e2e-test.sh` 的 E2「EMPLOYEE 查审计日志应 403」失败，实际返回 401。

**定位过程**：

1. 401 是"未认证"，403 是"已认证但无权限"——两者含义完全不同，说明 token 根本没被认出来；
2. 往回看脚本：前面的 C1a 用例**禁用了 zhangsan**，而禁用会执行"删除该用户全部登录会话"
   （第 5 周的"禁用即踢下线"），于是脚本开头生成的 EMPLOYEE token 在这时已经失效；
3. 也就是说这条用例测的不是"权限不足"，而是"登录态已失效"——是**测试自己制造的状态污染**。

**根因**：测试脚本里"破坏性步骤"（禁用账号）与"依赖该账号登录态的步骤"顺序冲突，
且没有在破坏性步骤后重建登录态。

**修复**：把"恢复 zhangsan 启用 + 重新分配 EMPLOYEE 角色 + 重新登录刷新 `emp_login.json`"
这一段整体前置到权限用例之前（D 段），并在注释里写明为什么必须这样排
（顺带把"禁用踢下线导致 token 从 403 变 401"这个真实行为记录在案——
它本身就是第 5 周功能的正确表现）。

**沉淀的规矩**：

- 写端到端脚本时，**先画出"哪些用例会破坏登录态/数据状态"，把恢复步骤紧跟在破坏步骤之后**，
  而不是统统堆在脚本末尾；
- 断言 401 与 403 要严格区分：**401 永远不能算作"权限被正确拦截"的证据**。

## BUG7-3（测试断言问题）：拿"隔了好几步"的基线去比对本步结果

**现象**：`keyrotation-e2e-test.sh` 的 K12 失败：期望 `reencrypted=6`（轮换前测的 k1 密文行数），
实际 `reencrypted=5`。

**定位过程**：

1. 先怀疑重加密漏了一行——去查 SQL，发现"全库 k1 残留 = 0"，说明该转的都转了；
2. 再回头看基线的测量时点：K6 在**轮换前**测到 6 行；而在轮换与重加密之间，
   K9a 通过实体更新改了 E001 的手机号；
3. 关键在 `EmployeeServiceImpl#update` → `baseMapper.updateById(employee)` 是**整行回写**：
   实体是被 TypeHandler 解密后的明文对象，回写时**该行所有敏感列都会用当前（新）密钥重新加密**——
   于是 E001 那一行在 K9a 时就已经整体切到 k2 了，K11 的残留校验也显示 5 行，与事实一致。

**根因**：测试基线跨过了"会改变该指标的动作"仍然复用，基线失效；
应用行为（整行重加密）是对的，并且其实是个**好性质**——普通编辑动作顺手把该行老密钥列也带成了新密钥。

**修复**：在重加密调用**紧前面**重新测量基线（`STALE_NOW`），并用它做断言。

**沉淀的规矩**：

- **基线要贴着被测动作测**，不能跨过任何可能影响该指标的写入；
- 顺带得到一个可以写进文档/答辩的观察：实体整行回写会让"编辑"顺带完成部分重加密，
  但**不能依赖它做轮换**（未被编辑的行、被逻辑删除的行不会经过这条路径），
  轮换收尾仍必须靠显式的重加密任务。

## BUG7-4（测试设计问题）：fail-fast 用例被更早的 fail-fast 抢先"证明"了

**现象**：`K28 KEK 缺失必须启动失败` 断言失败——进程确实非 0 退出了，
但输出里找不到 KEK 相关报错。

**定位过程**：

1. 手工复现：在临时目录（读不到 `application-local.yml`）里 unset `AES_MASTER_KEY` 启动，
   报错是 `JWT 密钥未配置：请设置环境变量 JWT_SECRET…`；
2. 原来 `JwtUtil` 的初始化早于 KEK 的初始化，**应用在到达 KEK 检查之前就已经失败退出了**；
3. 所以这条用例此前是"靠另一个原因通过"的——它证明了"缺配置起不来"，
   却**没有证明"KEK 缺失会 fail fast"**。

**根因**：fail-fast 用例的构造条件不完整（只去掉了一个必需配置，剩下的必需配置仍在缺失）。

**修复**：用例里显式补上 `JWT_SECRET`，只留 KEK 缺失这一个变量；
断言关键字改用 ASCII 的 `AES_MASTER_KEY`（见下一条观察），避免中文编码问题。

**沉淀的规矩**：

- 验证"某个配置缺失必须启动失败"时，**必须让其余必需配置齐备**，
  否则测到的是"启动失败"这个泛化结论，而不是目标配置的 fail fast；
- 这类用例值得单独花时间构造：fail fast 是安全系统的底线性质，退化成"带默认密钥启动"极难在事后发现。

## BUG7-5（前端文案）：提示框里 Markdown 星号裸露（第 5 周同类问题复发）

**现象**：浏览器实测截图里，密钥管理页与审计页的提示条显示
`且**只以密文形式**存在 sys_data_key 表里`、`明细里刻意**不写身份证…**`——
Element Plus 的 alert 不渲染 Markdown，星号原样显示。

**根因**：写文案时习惯性用了 Markdown 加粗，前端不做 Markdown 渲染。
**这与第 5 周的 BUG5-2 是同一类问题**（当时是 `**xxx**` 裸露在页面上）。

**修复**：去掉两处 `**`，改为纯文本。

**沉淀的规矩**：

- **"页面上的文案"一律不要写 Markdown 标记**（前端只有纯文本插槽）；
  这条在第 5 周已经记过一次，这次是复发——所以把它升级成硬规矩：
  新增页面/提示文案时，写完先自问"这段会不会被原样显示"；
- 视觉验证（截图）是这类问题**唯一可靠**的发现手段：
  接口测试全绿、构建无警告，星号依然裸露在页面上。

## BUG7-6（前端布局）：表格列宽总和超出容器，时间列被裁切

**现象**：密钥管理页截图中，"退役时间"列显示为 `2026-09-29 18:0`（末尾被裁掉），
右侧固定列（操作）还压住了内容。

**根因**：新增的 7 个列宽相加（90+140+220+120+180+180+120 = 1050px）超过了内容区可用宽度
（约 996px），Element Plus 固定列 + 超宽表格导致末尾列被压缩裁切。
**与第 5 周 BUG5-5（列宽超出容器致列被裁切）同类。**

**修复**：把固定宽度列收紧（keyId 80、状态 130、指纹 110、两个时间列 175、操作 90）+
唯一弹性列 `min-width: 180`，总和 ≈940px 留出余量；改后截图确认时间完整显示。

**沉淀的规矩**：

- 新表格页落地时**先算一遍列宽总和**（可用宽 ≈ 视口宽 − 220 侧栏 − 32×2 内边距），
  比"截图上肉眼发现"更省时间；
- 日期时间列建议固定 175~180px（`yyyy-MM-dd HH:mm:ss` 实测约需 160px + 内边距）。

## 测试过程中的重要观察（非缺陷，但值得记住）

1. **异步落库让断言方式必须改**：审计是 `@Async` 写入，接口返回时记录可能还没入库。
   脚本统一用"轮询直到预期值（最长 6s）"的 `wait_sql`，而不是"发完请求立刻查库"或"sleep 3 秒赌一把"。
   这是异步设计对测试的直接影响，写进了 `docs/audit-design.md`。
2. **`@Async` 是否生效，看线程名最快**：打开
   `logging.level.com.hrsecurity.audit=DEBUG` 后，日志里写入线程是 `audit-1`
   （自定义池的前缀）而不是 `http-nio-8080-exec-*`，这是"确实异步了"的直接证据；
   若打印的是 http 线程名，多半是踩了"同类内部调用不走代理"。
3. **新增 AOP 需要显式依赖**：Spring Boot 只自动配置 `spring.aop`，
   不会自动带 `@Aspect` 需要的 aspectjweaver，所以 pom 里补了 `spring-boot-starter-aop`；
   漏加的表现是启动期/运行期类找不到或切面不生效。
4. **Git Bash 下 grep 会把日志当二进制文件**：应用日志含中文 UTF-8 时，
   不带 `-a` 的 `grep` 可能判定为 binary 而**不输出任何匹配**（看起来像"没有日志"），
   排查这类问题时统一用 `grep -a`。
5. **`sys_data_key` 引导只在"表为空"时发生**：如果把库重灌（`init.sql`）但**不重启应用**，
   内存里仍是旧 DEK、库里却是空的——此时写入的密文用着一把"库里不存在的 keyId"。
   本地回归的正确顺序是：重灌 SQL → **重启应用** → 再跑测试（脚本头部的操作顺序说明已写明）。
6. **逻辑删除的数据也要轮换**：`@TableLogic` 会让 MP 的读写自动带 `status=1`，
   离职员工的密文用 MP 的实体 API 永远碰不到；这也是重加密改用 JdbcTemplate 的直接原因
   （见 `docs/key-management.md` 第 5.1 节）。
7. **审计的 `detail` 只能记"字段名"**：`sensitiveHint` 与 `AuditTrace` 里刻意只写
   "身份证/手机号/银行卡/工资"这些字段名，绝不拼接值——测试 A5/C5d 把这条红线固化成了断言。
