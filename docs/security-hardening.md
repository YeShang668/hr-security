# 安全加固与对抗性测试（第 8 周）

> 论文用途：可直接改写为**第 7 章 安全加固与测试**的底稿。
> 配套可执行证据：`test-payloads/security-e2e-test.sh`（**52 条用例**，本地全量回归 228/228 的一部分）。
> 上一阶段（第 7 周）完成的是"加密 → 脱敏 → 密钥生命周期 → 可追责"的**功能与数据安全**闭环；
> 这一周回答另一个问题：**有人来打，挡不挡得住、有没有证据**。

## 0. 一句话结论

本轮加固做的是"把已经存在的安全设计**证明出来**"，而不是堆新功能：
新增的 4 处代码改动都指向同一个原则——**校验要发生在它该发生的位置**（限流在密码校验之前、
强度校验在写库之前、转义在拼 SQL 之前、安全头在每个响应上）。剩下的价值全部落在
可复现的用例、矩阵和数字上（"我加了限流"远不如"5 次失败锁 10 分钟，12 条用例覆盖"）。

## 1. 越权矩阵（本系统的权限真相表）

这是本轮的核心交付物。规则：**每一格都有自动化断言**，脚本里对应 `V1~V14 / H1~H4`。
"未登录"列的 401 是 HTTP 状态码；EMPLOYEE/ADMIN 列的 403/200 是**业务 code**
（本项目业务错误统一走 HTTP 200 + body.code，见 README 的环境备忘）。

| 接口 | 权限要求（后端） | 未登录 | EMPLOYEE | ADMIN | 用例 |
|---|---|---|---|---|---|
| `POST /api/auth/login` | 白名单 | 200 / 400 / **429** | 同左 | 同左 | B1~B6 |
| `POST /api/auth/register` | 白名单 | 200 / 400 / 409 | 同左 | 同左 | B7~B10 |
| `POST /api/auth/logout` | 白名单（内部解析 token） | 200 | 200 | 200 | R5 |
| `GET /api/auth/me` | 认证 | **401** | 200 | 200 | V1 同源 |
| `GET /api/employees` | ADMIN \| EMPLOYEE | **401** | **200**（只读，字段脱敏） | 200 | V1 / V13 |
| `GET /api/employees/{id}` | ADMIN \| EMPLOYEE | 401 | 200 | 200 | — |
| `GET /api/employees/search` | `employee:sensitive:read` | 401 | **403** | 200 | V9 / I6 |
| `GET /api/employees/{id}/sensitive` | `employee:sensitive:read` | 401 | **403** | 200 | V8 |
| `POST /api/employees` | ADMIN | 401 | **403** | 200 | V11 |
| `PUT /api/employees/{id}` | ADMIN | 401 | **403** | 200 | **H1** |
| `DELETE /api/employees/{id}` | ADMIN | 401 | 403 | 200 | — |
| `GET /api/depts` | ADMIN \| EMPLOYEE | 401 | **200** | 200 | V14 |
| `POST/PUT/DELETE /api/depts` | ADMIN | 401 | **403** | 200 | V12 |
| `GET /api/users` | ADMIN | 401 | **403** | 200 | V4 |
| `PUT /api/users/{id}/status` | ADMIN | **401** | **403** | 200 | V2 / **H2** |
| `PUT /api/users/{id}/roles` | ADMIN | 401 | **403** | 200 | **H3** |
| `GET /api/roles` | ADMIN | 401 | **403** | 200 | V10 |
| `GET /api/audit-logs` | ADMIN | 401 | **403** | 200 | V5 |
| `POST /api/admin/crypto/backfill` | ADMIN | 401 | **403** | 200 | V7 |
| `GET /api/admin/keys` | ADMIN | 401 | **403** | 200 | V6 |
| `POST /api/admin/keys/*` | ADMIN | 401 | 403 | 200 | 9.8 |

矩阵里有两类"非禁止格"，第二类最容易被忽略，但恰恰是面试会被追问的：

1. **对照组（V13/V14）**：矩阵不能只有"禁止"。没有对照就分不清"权限策略收紧"和"接口整体挂了"——
   一次全 403 的回归看起来"很安全"，其实是服务坏了。
2. **已知边界（H4）**：`EMPLOYEE` 可以读到**全部部门**的员工列表（只读 + 字段脱敏），
   因为本系统的权限模型是**角色级**的，没有"数据归属/部门数据范围"这一层。
   这是设计取舍不是漏洞，但要主动说清楚：真实 HR 系统通常需要"部门经理只能看本部门"，
   那就得在查询条件里注入数据范围（或引入数据权限框架），属于本项目的**已知不覆盖项**。

**水平越权怎么测**：本项目没有"对象归属"概念，所以水平越权落在两处——
① 不能改**别人**的档案（H1）；② 不能改**自己**的角色来提权（H3，这是"自己越权自己"的经典形态，
防的是"合法用户拿合法接口做非法组合"）。两处都断言 403，且失败尝试都进审计（`result=FAILURE`）。

## 2. 本轮 4 处加固改动

| # | 改动 | 位置 | 为什么是这个位置 |
|---|---|---|---|
| 1 | **安全响应头**（nosniff / X-Frame-Options / Referrer-Policy / CSP / HSTS） | `SecurityConfig` + `docker-build/nginx/hr.conf` | 纯 JSON API 也值得加：接口可能被 iframe 嵌、被当 HTML 打开；且这是零成本的纵深防御 |
| 2 | **登录失败限流**（账号 5 次 / IP 20 次 / 锁 10 分钟，Redis 计数） | `LoginAttemptService` + `AuthServiceImpl.login` | 必须**先于密码校验**；计数放 Redis 是因为多实例共享且重启不清零 |
| 3 | **注册口令强度**（8~32 位，必须含字母与数字） | `RegisterDTO` | 校验必须在**写库之前**（B9 断言"被拒的口令没有落库"） |
| 4 | **LIKE 通配符转义** | `LikeUtils` + 员工/用户列表查询 | 参数化只防"改写 SQL 结构"，`%`/`_` 是**值语义**，参数化拦不住 |

### 2.1 响应头与 CSP 的取舍

- `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'` 用在**接口**上：
  本服务只产出 JSON，不需要加载/执行任何资源，直接全禁最省事也最安全。
- 前端页面用的是另一套 CSP（在 Nginx 里，见 `docs/deployment-https.md`）：
  必须允许 `'self'` 的脚本与样式，否则 SPA 起不来。两处的 CSP 不同是**刻意的**，
  因为一个是"数据接口"、一个是"应用页面"，威胁模型不同。
- **HSTS 只在请求本身是 https 时下发**（Spring Security 用 `request.isSecure()` 判断），
  这依赖 `server.forward-headers-strategy: native` 让反代后的 https 被识别（S5/S6 两条用例正反都测）。
  这也是抓"反代后应用以为自己是 http"这个经典坑的地方。

### 2.2 登录防护的设计取舍（重点）

| 维度 | 阈值 | 针对的攻击 | 为什么阈值不同 |
|---|---|---|---|
| 账号 | 5 次 / 10 分钟 | 死磕一个账号猜密码 | 更严：单个账号被爆破的直接损失最大 |
| IP | 20 次 / 10 分钟 | 一个 IP 撞很多账号（撞库） | 更宽：避免"故意输错把别人账号锁死"的**拒绝服务反噬**（多用户共用出口 IP 时尤其明显） |

三个必须说清楚的细节：

1. **限流在密码校验之前**：否则锁定期的"正确密码"仍然能登录进去，锁定形同虚设。
2. **成功登录只清账号计数，不清 IP 计数**：账号计数要清（避免"白天错 4 次、晚上再错 1 次被锁"的误伤）；
   IP 计数要留，否则攻击者只要手里有一个能登录的账号，就能不断"清零"自己的撞库额度。
3. **固定锁定期而非指数退避**：实现简单、可解释；生产建议改成"失败越多锁越久"（写进已知不覆盖项）。

### 2.3 参数化 ≠ 值语义安全

`#{}` 参数化保证了"用户输入永远进不了 SQL 结构"，但拿到经典注入串 `' OR '1'='1` 时，
参数化后它变成一个**字面量**，匹配不到任何行（I1~I3 断言 200 且 0 条）——这一层是对的。

真正的洞在**通配符**：`keyword=%` 会变成 `LIKE '%%%'`，**命中全表**。
它不是注入（没改写结构），但效果是"一个字符把整张表拉出来"（数据枚举 + LIKE 无法走索引）。
第 8 周加了 `LikeUtils.escape()`（转义 `\ % _`，依赖 MySQL 的默认转义符，不拼 ESCAPE 子句），
I4/I5 两条用例把它钉住：加固前 `total=3`，加固后 `total=0`。

**顺带复查了动态拼 SQL 的地方**（第 7 周重加密按密文列前缀批量处理）：
那里的列名/前缀来自内部常量与 `sys_data_key.key_id`，**没有任何用户输入进入 SQL 结构**，
所以没有引入白名单之外的风险。这类场景的正确做法就是"白名单常量"，不是转义。

## 3. 注入 / XSS / CSRF / 爆破：结论与证据

| 类别 | 结论 | 证据（用例） |
|---|---|---|
| SQL 注入（列表/搜索/登录） | 参数化 + 通配符转义后，注入串只按字面量匹配，无 500/异常 | I1~I8 |
| SQL 注入（动态列名） | 无用户输入进入 SQL 结构（代码审计 + 文档记录） | 见 2.3 |
| 存储型 XSS | 输入**原样存储**，靠**输出编码**防执行（Vue 插值默认转义）；接口 `Content-Type: application/json`；前端 0 处 `v-html` | X1~X6 |
| CSRF | **不适用**，且用"只带 Cookie 的请求拿不到认证"证明了前提不成立 | S7 / S8 |
| 爆破/撞库 | 账号 5 次锁 10 分钟；锁定不影响其他账号；失败全部进审计 | B1~B6、B11 |
| 弱口令 | 注册入口强制 8~32 位含字母数字；被拒请求不落库 | B7~B10 |
| 安全响应头 | nosniff / DENY / no-referrer / CSP / HSTS（仅 https） | S1~S6 |

关于 XSS 有一个刻意的选择要讲清楚：**我们不做"输入过滤"**（不把 `<script>` 从姓名里删掉）。
因为过滤输入会破坏数据本身（"这家公司真的叫 A<B"），而且永远列不全黑名单；
正确做法是**在输出处按上下文编码**（HTML 文本、属性、JS、URL 各自的编码规则不同），
浏览器端 Vue 的插值已经做了这件事，我们只需要保证"没有绕过它的写法"（所以 X6 断言 0 处 `v-html`）。
另外，接口是以 `application/json` 返回的，浏览器不会把 JSON 内容当 HTML 渲染执行——这是第二道防线。

## 4. 已知不覆盖项（主动交底，比藏着强）

1. **无数据级权限**：角色级授权，`EMPLOYEE` 可见全量员工列表（H4 明确断言了这个边界）。
   要支持"部门经理只看本部门"，需要引入数据范围（DataScope）机制。
2. **无弱口令字典/已泄露口令库校验**：只做"长度 + 字符种类"，`P@ssw0rd` 这类可预测变形能通过。
3. **限流是固定锁定期，不是指数退避**；且只覆盖登录接口（注册、短信等可枚举接口未限流）。
4. **IP 维度依赖 `X-Forwarded-For`**：在可信代理后面才准确；没有代理直连时可被伪造（账号维度才是主防线）。
   本项目通过 Nginx **重置**该头来收窄这个风险（`https-e2e-test.sh` T12 断言伪造失效）。
5. **未做真实渗透测试**：只做"可复现的自动化加固验证"，没有 WAF、没有扫描器、没有 0day 类测试。
6. **未做依赖漏洞扫描**（SCA）与镜像扫描：生产应在 CI 里加 `trivy`/`dependency-check`。
7. **证书是自签**（本地/CI 无法申请公网证书），生产必须换 Let's Encrypt 或商业 CA。
