# 第 6 周 Bug 与踩坑记录（敏感字段 AES-256-GCM 加密 + 动态脱敏）

> 记录规则：只记"当时现象 → 定位过程 → 根因 → 修复 → 沉淀成什么规矩"，
> 方便以后回看时能复用判断，而不是只看到一个结论。

## BUG6-1（重要）：TypeHandler 只对写入生效，读出来还是密文

**现象**：新链路第一次冒烟，ADMIN 调 `GET /api/employees` 返回的敏感字段是
`v1:k1:KvOvBkZbCNWM2xga:KZFKgu5/f8YuEPIlo4KghlRNAkMWWoKaEY7l` 这样的密文串，
而不是明文；EMPLOYEE 调用时更是把密文当明文做了脱敏，输出
`v1:****************************************************EY7l`（一眼假）。

**定位过程**：

1. 先怀疑 TypeHandler 没生效 —— 但直连 MySQL 查 `id_card_enc` 确认**写进去的是密文**（格式正确、含 keyId），
   说明写入方向（`setNonNullParameter`）是好的；
2. 再看读取方向：`SELECT` 回来的是原始列值，说明 MyBatis 用了**默认的字符串映射**，没走我们的 handler；
3. 查 MyBatis-Plus 文档确认：实体上用 `@TableField(typeHandler = ...)` 时，
   **`@TableName` 必须显式加 `autoResultMap = true`**，否则默认的实体结果映射不包含自定义 TypeHandler，
   只有 SQL 参数（写入）会用它。

**根因**：MyBatis-Plus 的默认 resultMap 由实体字段元数据生成，不自动携带 `typeHandler` 配置；
`autoResultMap = true` 才会生成带 `typeHandler` 的结果映射供查询复用。

**修复**：`@TableName(value = "sys_employee", autoResultMap = true)`（见 `SysEmployee`）。

**沉淀的规矩**：

- 用 TypeHandler 做字段加解密，**必须同时检查"写进去"和"读出来"两个方向**，
  只验证落库格式很容易漏掉读取方向；
- 修复后新增回归用例 C2a（明文接口往返）与 C7c（迁移后解密），把这条经验固化成断言；
- 附带发现：**脱敏逻辑作用在密文上没有意义**，所以在 `toVO` 里只能对已解密的明文做掩码——
  这次输出里出现"带星号的密文"本身就是这个 bug 的信号灯。

## BUG6-2（测试设计问题）：把"密文损坏"当成可以靠接口自修复

**现象**：加密专项脚本跑到 C5（篡改密文验证 GCM 完整性）之后，C5b「运维重新加密后恢复正常」
以及紧随其后的 C6a/C8a/C8f/C8g 共 5 条用例全部失败，返回 500。

**定位过程**：

1. 看应用日志，异常是 `密文完整性校验失败（数据被篡改或密钥不匹配），拒绝解密`；
2. 想通链路：C5a 用 SQL 把 `E200.id_card_enc` 改坏后，**这一行就再也读不出来了**；
   而 C5b 想通过 `PUT /api/employees/{id}` 修复它，PUT 的第一步是 `selectById` → 解密 → 直接抛异常。
   所以"用接口修好被篡改的行"这个前提根本不成立，后面依赖该行的用例自然连锁失败。

**根因**：测试用例的假设不成立（把不可读的行当成可通过接口自修复），
不是应用缺陷。这背后其实是本周刻意选择的行为：**密文坏了就读失败（fail loud）**，
绝不静默降级返回乱码或 null。

**修复**：把 C5b 改成真实的运维恢复流程——先 `UPDATE ... SET id_card_enc = NULL` 清掉不可读的密文，
再通过接口重新录入，然后断言能正常解密（C5c）。用例之间的状态依赖也因此显式化了。

**沉淀的规矩**：

- 破坏性用例（篡改数据）必须自带恢复路径，且恢复手段要符合真实运维流程；
- "失败行为"也是设计的一部分：本次把"读失败"写进 `crypto-design.md` 的取舍表，
  连代价（该行在修复前读不出来）一起写清楚，答辩时正面回答比含糊过去更可信。

## BUG6-3（前端小瑕疵）：占位文案重复"如"

**现象**：新增员工弹窗里工资输入框的提示是"如 如 18000.00"。

**根因**：`sensitivePlaceholder(sample)` 内部已经拼了 `如 ` 前缀，调用处又传了 `如 18000.00`。

**修复**：调用处改为 `sensitivePlaceholder('18000.00')`，与其它字段一致。浏览器实测已确认。

## 测试过程中的重要观察（非缺陷，但值得记住）

1. **脱敏策略在实现中途收紧过一次**：最初列表对"有敏感权限的人"直接返回明文（只对无权者脱敏），
   实测时发现这样"明文是被列表顺手带出来的"，与"明文必须是显式动作"的设计目标不符，
   于是改成**列表/详情对所有角色一律脱敏，明文只从 `/sensitive` 出口出**。
   对应改动：`EmployeeServiceImpl#toVO` 不再接收权限开关，统一走 `MaskingUtil`；
   前端"查看完整信息"按钮对 ADMIN 同样有意义了。
2. **前端编辑弹窗刻意不回填敏感字段**：列表里是 `137****5678`，如果回填到表单再保存，
   掩码就会被当作新明文加密写库。前端留空 + 后端"空则不覆盖" + DTO 正则拦截，三道防线。
   浏览器实测：编辑只改姓名后，`查看完整信息` 里的身份证/手机号/银行卡/工资原值不变。
3. **自动化环境限制**：Element Plus 的下拉框（部门选择）在本项目的自动化测试环境里
   无法用常规 locator 点击打开（元素被透明占位层覆盖、`tabindex=-1`，键盘 `ArrowDown` 也不展开），
   最终用"读取元素几何中心 + 坐标点击"完成选择。
   这是测试工具的限制，不是页面缺陷（人工点击正常）；
   因此"新增员工"的完整 GUI 提交链路仅验证过一次，而同等逻辑由接口用例 C1a/C8 持续覆盖。
4. **Redis 缓存键增加**：权限编码缓存 `user:perms:{userId}` 与角色缓存一起在 `evict` 里删除。
   如果只删角色缓存，会出现"角色已改、敏感明文权限还残留 30 分钟"的窗口期——
   这类"缓存漏删"是权限系统里最隐蔽的一类问题，所以两把键的删除写在同一个方法里，不靠调用方记得。
