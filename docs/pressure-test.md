# 压测：给"加密 + 审计"的开销定价（第 8 周）

> 论文用途：可作为**第 7 章 性能测试与分析**的底稿（内含原始数据表与结论）。
> 可执行证据：`test-payloads/pressure-test.py`（Python 标准库实现，见 §1 的选型说明）。
> 测试时间：2026-10-03；**原始结果已入库**：`docs/pressure-results/pressure-c8.json`（并发 8）与
> `pressure-c16.json`（并发 16），由脚本 `--json` 直接输出，下表就是它们的可读版本。

## 0. 一句话结论

**加密与审计都不是瓶颈。** 单个敏感字段读取（4 个字段解密 + 一次异步审计投递）的业务方法耗时
**平均 0.9 ms**，端到端 P95 只有 7.4~9.4 ms，比"脱敏列表"还快；本轮压测中真正的瓶颈是
**登录的 BCrypt 成本（约 65 ms/次，CPU bound）**和**列表接口的查询形态**（每请求 2 条 SQL）。
并发审计在 2×300 次请求下 **300/300 全部落库，零丢失**。

## 1. 工具与方法（含选型理由）

为什么不是 k6/JMeter：两者都更适合做压测（场景脚本 + 丰富指标），但**本机与 CI runner 都没预装**，
引入外部二进制会让"能否复现"变成环境问题。本脚本用标准库线程 + 持久连接
（`http.client`，避免把建连开销混进被测接口）已经能给出可信的 QPS 与分位延迟，
而且能在**同一进程里**顺手完成"并发下审计不丢"的一致性校验（拿 MySQL 行数与请求数比对）——
这一点 k6 反而要靠外部脚本配合。要做持续压测基线时再补 k6（见 §6）。

三类场景对应三条不同的开销路径：

| 场景 | 请求 | 每次请求做了什么 |
|---|---|---|
| `login` | `POST /api/auth/login` | BCrypt 校验（故意慢）+ 查库 + 写 Redis 会话 + 写审计 |
| `list` | `GET /api/employees?page=1&size=10` | 分页查询（`COUNT(*)` + `ORDER BY` + `LIMIT`）+ 部门名批量查询 + 脱敏 |
| `sensitive` | `GET /api/employees/{id}/sensitive` | 主键查一条 + **AES-GCM 解密 4 个字段** + **异步落一条审计** |

运行方式：

```bash
# 应用以 jar 形式跑在本机（JDK 25 / MySQL 8.4 / Redis 8.10，同一台笔记本）
MYSQL_CMD="mysql --default-character-set=utf8mb4 -uroot hr_security -e" \
  python test-payloads/pressure-test.py --scenario all --concurrency 8 --requests 300 --check-audit
```

## 2. 原始结果

**测试环境**：Windows 11 单机，JDK 25（进程按 17 编译运行）、MySQL 8.4.9、Redis 8.10.1
**与应用同机**（不是独立压测环境）。因此**绝对 QPS 不可移植**，有意义的是**场景间的对比**
与**并发下的一致性结论**。

### 并发 8（每场景 300 请求）

| 场景 | 成功/总数 | 错误率 | QPS | avg | P50 | P95 | P99 | max |
|---|---|---|---|---|---|---|---|---|
| login | 300/300 | 0% | 121.8 | 65.0 ms | 63.2 ms | 79.4 ms | 87.8 ms | 90.4 ms |
| list | 300/300 | 0% | 945.1 | 8.3 ms | 8.0 ms | 10.9 ms | 15.7 ms | 19.6 ms |
| sensitive | 300/300 | 0% | **1306.2** | 6.0 ms | 5.9 ms | **7.4 ms** | 11.5 ms | 15.4 ms |

审计一致性（sensitive 场景）：请求 **300** 次，审计行 200 → **500**（期望 ≥500），
**缺失 0 条**；审计记录里的业务方法耗时 avg **0.9 ms** / P95 1 ms / max 4 ms（样本 500）。

### 并发 16（每场景 300 请求）

| 场景 | 成功/总数 | 错误率 | QPS | avg | P50 | P95 | P99 | max |
|---|---|---|---|---|---|---|---|---|
| login | 300/300 | 0% | 227.7 | 68.5 ms | 67.5 ms | 77.7 ms | 90.0 ms | 95.5 ms |
| list | 300/300 | 0% | 1509.1 | 10.3 ms | 10.1 ms | 13.9 ms | 16.0 ms | 29.9 ms |
| sensitive | 300/300 | 0% | **2244.9** | 7.0 ms | 6.8 ms | **9.4 ms** | 11.0 ms | 20.3 ms |

审计一致性：请求 **300** 次，审计行 500 → **800**，**缺失 0 条**；
业务方法耗时 avg 0.9 ms / P95 2 ms / max 4 ms（样本 800）。

## 3. 结论与瓶颈定位

### 3.1 加密不是瓶颈（反直觉，但数据很清楚）

`sensitive` 单请求的业务方法（查主键 + 解密 4 个字段）平均 **0.9 ms**，
占端到端 avg 6~7 ms 的约 **13%**；其余是 HTTP/JSON/框架开销。
也就是说"字段级 AES-GCM 会不会把系统拖慢"的答案取决于**每次解密的字段数**，
本场景 4 个字段 ≈ 0.9 ms，属于可接受量级。

### 3.2 登录的瓶颈是 BCrypt（CPU bound）

并发 8 → 16，QPS 从 121.8 → 227.7（**+87%**），而 **P95 基本不动（79.4 → 77.7 ms）**。
P95 不随并发恶化说明**没有排队**，即系统还没饱和，瓶颈是"每次请求固定要花 ~65 ms 的 CPU 时间"
（BCrypt cost=10 的设计目标就是慢，这是**安全特性不是缺陷**）。
推论：登录吞吐 ≈ CPU 核数 / 单次哈希耗时。
**优化方向不是"把 BCrypt 调快"**（那是拿安全性换吞吐），而是：
① 多实例水平扩展（登录本身无状态，会话在 Redis）；② 前端体验上做登录按钮防抖；
③ 极端场景才考虑把登录校验拆到独立服务/独立线程池，避免拖累其它接口。

### 3.3 列表接口比"明文读取"还慢，原因是查询形态

`list`（945/1509 QPS）**慢于** `sensitive`（1306/2245 QPS），初看反直觉，原因是**每请求的 SQL 次数**：

- `list`：`selectPage` → 一条 `COUNT(*)`（分页总数）+ 一条 `SELECT ... ORDER BY id DESC LIMIT`（深分页形态）
  + 一条部门名批量查询 = **3 条 SQL**，且 `COUNT(*)` 与 `ORDER BY ... LIMIT` 都是随数据量增长的成本项；
- `sensitive`：一条主键等值查询 = **1 条 SQL**。

也就是说，**这里的性能差异来自"取数方式"，与加密无关**。数据量再大一个量级时，
`COUNT(*)` 与 `LIMIT offset` 会进一步恶化——优化方向是"延迟计数/近似计数 + 键集分页（keyset pagination）"，
而不是去优化解密。并发从 8 升到 16 时 `list` 的 P95 从 10.9 → 13.9 ms（劣化 28%），
也印证它比 `sensitive` 更早出现竞争（多条 SQL 抢连接/锁）。

### 3.4 审计的异步设计有效，且并发下不丢

三条证据：

1. **审计没有体现在请求延迟里**：`sensitive`（每次都写审计）比 `list`（不写审计）还快，
   说明 `@Async` + 独立线程池确实把审计移出了请求路径。
2. **并发 2×300 次请求，审计行 0 缺失**（500→500、800→800）。
   第 7 周设计的线程池（core 2 / max 8 / queue 500 / `CallerRunsPolicy`）在这轮规模下
   连队列都没打满，兜底策略未被触发。
3. 审计记录里自带"方法耗时"字段，使"业务耗时"与"端到端耗时"可以分开看
   （0.9 ms vs 6~9 ms），这正是评估开销时最需要的切分。

## 4. 局限（主动交底）

1. **单机同测**：压测客户端、应用、MySQL、Redis 在同一台笔记本上抢 CPU，
   绝对数字不可移植；结论只用于**相对比较**。
2. **规模不足以打到审计队列上限**：queue 500 / max 8 在这个量级下毫无压力，
   "审计线程池饱和后会怎样（`CallerRunsPolicy` 退化为同步写）"**没有被压出来**。
   要验证它需要"持续高并发 + 慢库"的组合（写进 §6 下一步）。
3. **没有做长稳测试**（如 30 分钟持续压测看内存/连接池/GC），也没有采集 GC/线程数指标。
4. **没有对比"关掉审计"的对照组**：本轮用"`list` vs `sensitive`"近似替代，
   但两者查询形态不同（§3.3），所以"审计开销"和"查询差异"混在一起，只有"方法耗时 0.9 ms"是纯净化数据。
5. **未测 HTTPS/反代链路**：本轮全走 http 直连 8080，TLS 握手与 Nginx 反代的开销没有度量。

## 5. 下一步（按性价比排序）

1. **把审计的方法耗时提升为独立数值列**（`sys_audit_log.elapsed_ms`）：现在它只写在 `detail` 文本里，
   只能靠正则从字符串里抠（见 `docs/week8-bugfix-log.md` BUG8-4）。有了列就能直接做耗时聚合与慢操作排行。
2. **列表接口改造**：延迟计数 / 键集分页，把每请求 SQL 次数从 3 降到 1~2（这是当前最大的可优化项）。
3. **打到审计队列上限**：把 queue 调小 + 人为让 MySQL 变慢，验证 `CallerRunsPolicy` 的降级行为
   与"降级后请求延迟如何变化"——这是"绝不丢审计"承诺的边界验证。
4. **独立压测环境**：压测客户端与应用分离，采集 GC/线程池/连接池指标，形成可对比的性能基线。
5. 引入 k6 做回归型压测（CI 里跑小规模 + 阈值断言），把性能退化成 CI 的一道门。
