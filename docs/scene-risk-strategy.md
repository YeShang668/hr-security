# 人事敏感数据安全管控 · 场景-风险-策略调研小结

> 第 4 周（2026-09-06）交付物。导师要求：了解应用场景 → 选择一个感兴趣的 → 分析该场景的数据安全风险 → 制定安全策略。
> 本文档 = 毕设论文"设计"章节与面试"项目背景"的话术底稿。只讲与本系统实现强相关的结论，不堆砌概念。

## 1. 应用场景

企业人事管理系统集中存储员工的**个人敏感信息**（手机号、身份证、家庭住址、银行卡、工资等），并支撑招聘、考勤、薪酬、绩效等业务。此类数据的特点：

- **量大且长期保存**：员工从入职到离职后若干年都需保留，静态数据是攻击者的高价值目标；
- **敏感等级高**：身份证号、银行卡号属于个人敏感信息，泄露可能被用于身份冒用、精准诈骗；
- **多方可见**：HR、部门主管、财务、系统管理员都需要接触数据，但**"需要"与"需要全部明文"是两回事**——这是"最小权限 + 按需脱敏"的业务基础；
- **合规压力**：我国《个人信息保护法》《数据安全法》与等保 2.0（GB/T 22239-2019）对个人信息处理提出保密性、完整性、可审计要求，央企/国企人事系统是合规检查重点对象（也是本项目选题的现实依据）。

## 2. 资产识别（哪些是敏感数据）

| 资产 | 说明 | 敏感级别 | 当前状态 |
|---|---|---|---|
| sys_employee.phone / email 等 | 员工联系方式 | 高 | 明文占位（9/19 AES 周加密） |
| 身份证号 / 银行卡 / 工资（规划列） | 强敏感字段 | 极高 | 刻意**不落库**，加密周再 ALTER 添加（红线：不引入明文库） |
| sys_user.password | 登录凭据 | 极高 | BCrypt 密文（已落地） |
| JWT / Redis 登录会话 | 会话凭据 | 高 | 24h 会话 + 服务端可控失效（已落地） |
| 角色权限数据 | 访问控制依据 | 中 | 库表 + Redis 缓存（已落地） |
| 审计轨迹 | 事后追责依据 | 中 | 审计日志周（9/26）落地 |

## 3. 风险分析（威胁建模）

按"数据生命周期 × 攻击面"梳理，风险编号供第 4 节策略矩阵引用：

| 编号 | 风险 | 攻击面/成因 | 对标（OWASP Top10 2021 / 等保 2.0） |
|---|---|---|---|
| R1 | **明文存储泄露**：数据库被导出/备份丢失，敏感字段直接可读 | 拖库、DBA/运维越权访问、备份介质遗失 | OWASP A02 加密机制失效；等保-数据保密性 |
| R2 | **SQL 注入 / 接口滥用导致批量拖取** | 未参数化查询、接口无鉴权或越权 | OWASP A03 注入；等保-访问控制 |
| R3 | **越权访问（水平/垂直）**：普通员工能看/改他人敏感数据或管理接口 | RBAC 缺失或授权过期不即时生效（如角色已回收、旧 token 仍可用） | OWASP A01 访问控制失效；等保-访问控制 |
| R4 | **身份冒用与会话劫持**：token 泄露后攻击者长期可用、服务端无法踢人 | JWT 无状态、无过期或过期过长、登出不失效 | OWASP A07 认证失效；等保-身份鉴别 |
| R5 | **密钥泄露/管理不当**：加解密密钥与密文同库同文件、硬编码、无轮换 | 开发者将密钥写进代码/配置文件并提交 | OWASP A02；密钥管理最佳实践 |
| R6 | **审计缺失**：敏感数据被谁在何时查看/修改无记录，出事无法追责 | 未记录操作日志或日志不可信 | 等保-安全审计（GB/T 22239 要求审计覆盖每个用户） |
| R7 | **传输窃听**：明文 HTTP 传输敏感数据 | 内网抓包、公共 Wi-Fi | 等保-通信传输保密性 |
| R8 | **接口面过大**：内部组件端口对外暴露（如 MySQL/Redis 公网可达） | 端口映射过宽、默认配置 | 等保-网络架构（最小化服务暴露） |

## 4. 安全策略矩阵（风险 ↔ 对策 ↔ 本项目落地）

| 风险 | 对策 | 本项目落地模块 | 状态 |
|---|---|---|---|
| R1 明文存储 | **字段级 AES-256-GCM 加密**：只加密敏感字段，加密值带随机 IV，认证加密防篡改 | 员工表敏感字段加密服务（JDK javax.crypto，不造轮子） | 9/19 计划 |
| R1 / R5 | **KEK/DEK 两级密钥**：DEK 加密数据、KEK 加密 DEK，轮换只换 DEK；KEK 存环境变量/密钥服务，密文与密钥分离存储 | 密钥管理模块 | 9/26 计划 |
| R2 SQL 注入 | MyBatis-Plus 参数绑定 + 预编译（本项目无拼接 SQL）；逻辑删除防误删 | 数据层（已落地）+ 10 月防注入专项 | ✅/计划 |
| R3 越权 | **RBAC 最小权限**：接口级 @PreAuthorize 鉴权；**角色变更即时生效**（角色走 Redis 缓存、变更删缓存、旧 token 立即失效，不信任 JWT 内旧角色）；后续补行级数据权限 | SecurityConfig + JwtAuthenticationFilter + 角色缓存 | ✅ 已落地（9/19 后演进数据权限） |
| R4 会话 | JWT 24h + **Redis 会话同步 TTL**；登出/管理员可直接删会话"踢人"；坏 token/无会话一律 401 | AuthService + SessionService | ✅ 已落地 |
| R5 密钥 | 密钥**环境变量化**（JWT_SECRET），gitignore 兜底禁止入库；缺失即快速失败不弱密钥运行；Docker 用 .env/环境变量注入 | 第 4 周重构 + JwtUtil 守卫 | ✅ 已落地 |
| R6 审计 | **AOP 审计日志**：敏感字段访问/修改记录操作者、时间、IP、操作内容摘要 | audit 模块 | 9/26 计划 |
| R7 传输 | HTTPS（Nginx 终结 TLS + 证书） | 部署层 | 10/10 加固周 |
| R8 接口面 | Docker 化后 **MySQL/Redis 不对外发布端口**，只在内网供应用访问；数据库用专用低权账号（hr，仅授 hr_security 库） | docker-compose.yml（第 4 周） | ✅ 已落地 |
| 备份 | 备份文件加密 + 异地/定期恢复演练（落库字段已加密则备份本身即密文，双重保障） | 部署运维侧文档 | 第 3 阶段规划 |

**纵深防御结构（面试一图流）**：传输层 TLS → 应用层 RBAC 鉴权 → 字段级加密（密文落库）→ 密钥独立管理 → 审计留痕 → 备份/介质安全。任何一层被突破，数据仍不可直接读、操作可追溯。

## 5. 已有对策与本项目的差距

- 已具备：BCrypt、JWT+Redis 会话、RBAC+缓存即时生效、环境变量化、容器最小暴露、统一 JSON 错误（不给攻击者泄露堆栈）。
- 待补齐（按排期）：字段加密与脱敏（9/19）→ 审计 + KEK/DEK（9/26）→ 越权横向测试、注入/XSS、密钥轮换、HTTPS、压测（10 月）→ 前端登录传输保护随 Vue3 接入。
- 方法论差距（写论文时展开）：未做正式威胁建模（STRIDE），仅按场景清单化分析；等保/个保法只做"概念对齐"，不做合规声明。

## 6. 面试话术要点（30 秒版 + 追问准备）

> 项目背景：我做的是人事敏感数据安全管控系统。HR 系统里身份证、工资这类字段如果明文落库，一旦拖库或 DBA 越权，数据直接裸奔，而且《个保法》和等保都要求敏感数据加密存储和可审计。所以我的系统把"敏感数据安全"作为主线：登录用 BCrypt + JWT + Redis 会话，权限走 RBAC 最小权限且角色变更即时生效，身份证/工资这类字段后续做 AES-256-GCM 字段级加密 + KEK/DEK 两级密钥，敏感操作全部 AOP 审计，最后用 Docker Compose 一键交付，MySQL/Redis 不暴露公网。

追问准备：字段加密为什么用 AES-GCM（认证加密防篡改、JDK 内置）？KEK/DEK 为什么两级（轮换成本、泄露面）？角色变更如何即时生效（Redis 缓存 + 删缓存，旧 token 下次请求即失效）？登出如何失效（删 Redis 会话，验签后查会话）？加密后如何检索/排序（脱敏列冗余、不可检索即放弃该维度的检索——论文里设计取舍）。
