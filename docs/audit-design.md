# 审计日志设计（第 7 周）

> 用途：论文"设计"章节里"审计与可追责"部分的底稿；也可直接作为答辩/面试讲稿。
> 配套文档：`crypto-design.md`（字段加密与脱敏）、`key-management.md`（KEK/DEK 与轮换）。

## 1. 要解决什么问题

前面六周解决了"数据存得安全"（字段级 AES-256-GCM）与"看得见的分寸"（动态脱敏 + RBAC）。
但安全治理还差最后一块：**可追责**。具体是四个问题：

1. **明文出口无记录**：谁在什么时候看了谁的身份证/银行卡/工资？系统此前只有一个"明文出口"接口，
   但没有任何记录——出事后无法回答"这 200 条明文是谁导出去的"。
2. **权限变更无记录**：谁给谁加了管理员？谁把某个账号禁用了？这是提权类攻击最常见的落点。
3. **运维动作无记录**：批量加密迁移、密钥轮换这类"一次动全库"的动作，必须能回答"谁在什么时候执行过"。
4. **访问审计本身无记录**：能把审计日志翻一遍的人，等于能抹掉线索（现实中的"内鬼第一步"）。

审计模块的设计目标就是：**上述四类动作 100% 留痕，且"没看成"与"看成了"能区分开。**

## 2. 记录什么：五个问题 + 结果

表 `sys_audit_log` 的字段就是照着"事后取证要问什么"设计的：

| 问题 | 字段 | 设计说明 |
|---|---|---|
| 谁 | `user_id` + `username` | **冗余存 username**：用户改名或注销后，审计记录仍要能说清"当时是谁"。只存 id 会在用户表变更后失去可读性 |
| 何时 | `created_at` | 存**事件发生时间**（请求线程里取），不是异步线程插入的时间 |
| 做了什么 | `operation` | 操作类型，如"查看员工敏感信息""轮换数据加密密钥" |
| 对什么做的 | `target_type` + `target_id` | 目标用字符串存（兼容非数字主键）；targe_id 允许为空（如全库级运维动作） |
| 来自哪 | `ip` + `user_agent` | IP 取 `X-Forwarded-For` 最左地址（见第 5 节） |
| 结果如何 | `result` | `SUCCESS`/`FAILURE`——失败也要记，见第 3 节 |

另外三个刻意的约束：

- **只增不改不删**：`SysAuditLogMapper` 只提供 insert/select，没有 update/delete 方法；
  审计记录一旦写入即成为证据，应用代码没有篡改它的入口（真实生产还会加"只允许 INSERT 的数据库账号"）。
- **绝不写入敏感明文**：`detail` 只写"看过/改过哪些字段"，不写字段值。
  否则审计表自己会变成一张新的明文敏感数据表——**这是审计设计里最容易犯的错**（实测断言见 `audit-e2e-test.sh` A5）。
- **单页上限 100**：审计表是全库增长最快的表，不设上限时一个 `size=100000` 就能把整表拉走。

## 3. 关键取舍

### 3.1 成功和失败都记

失败记录的价值在于"**试图**做了什么"：反复刷无权限接口、拿别人的 id 试探、
禁用自己被红线拦下——这些行为只有在失败记录里才看得见。同时失败记录也是排障线索。

代价：一次"查不到员工"也要写一行审计。可接受（异步写入，对主流程无影响）。

### 3.2 未覆盖范围（必须写在明面上）

- **被 Spring Security 在方法执行前拦下的 403 不会进入切面**，因此这类越权尝试目前不留痕
  （本模块的 `result` 里也没有"DENIED"）。想覆盖它需要把埋点提到 Controller 层或用
  Spring Security 的 `AuthorizationDeniedEvent` 监听器。当前选择：业务方法层埋点（覆盖全、实现简单），
  越权靠"没有成功记录"来推断。测试用例 B1/B2 正是按这个口径写的：
  403 之后断言"没有 zhangsan 的 SUCCESS 记录"，而不是"有一条 FAILURE 记录"。
- **读取接口（列表/详情）不逐条记**：列表是高频动作，全记会把审计表灌爆，
  且"明文出口唯一"的设计本身就是为了让审计只盯一处。这是"数据最小披露"带来的审计收益。
- **审计写入失败不会阻断业务**：异步线程写库失败只打 ERROR 日志。
  取舍理由：审计是旁路需求，但**不能悄悄丢**——所以线程池拒绝策略选了 `CallerRunsPolicy`（见 4.2）。

### 3.3 为什么用注解 + AOP，而不是在方法里手写 insert

1. 不侵入业务：Service 只多一行 `@AuditLog(...)`；
2. 不遗漏且可审阅：`grep -r "@AuditLog" src/` 就能列出全部埋点清单，
   敏感动作是"必须有记录"的清单，让它在代码里一眼可见；
3. 一致：操作者、IP、UA、耗时的取法只有一份实现。

## 4. 实现要点与三个坑

### 4.1 切面必须放在事务外层（`@Order`）

审计切面用 `@Order(Ordered.HIGHEST_PRECEDENCE + 100)`，而 Spring 事务通知的 order 是
`LOWEST_PRECEDENCE`（最内层）。执行顺序因此是：

```
审计切面进入 → 开启事务 → 业务方法 → 提交事务 → 审计落库
```

两个收益：
- 记录时事务**已经真正提交**，不会出现"事务回滚了、审计却说成功"；
- 如果反过来（切面在事务内且同步写库），业务失败时连"失败"这条审计记录自己也会被一起回滚——
  这类"审计被业务事务牵连"的问题很隐蔽。

### 4.2 异步落库：@Async + 自定义线程池

```java
@Async("auditExecutor")  // AsyncConfig：core 2 / max 8 / queue 500 / CallerRunsPolicy
```

- **为什么要异步**：审计不该让用户"查看明文"的响应多等一次数据库写；
  审计表增长最快，同步写在高峰期会直接拖慢接口。
- **为什么必须自定义线程池**：Spring Boot 给 `@Async` 的默认执行器是
  `SimpleAsyncTaskExecutor`——**每次调用新建线程、不复用、不限并发**，高并发下线程数会失控。
- **为什么拒绝策略选 CallerRunsPolicy**：队列满时让调用线程自己写库，相当于自动降级成同步。
  宁可让接口慢一点，也**不丢审计记录**（丢记录比慢一点严重得多）。

### 4.3 三个坑（本周实际踩过/提前防住的）

| 坑 | 说明 | 本项目做法 |
|---|---|---|
| 同类内部调用不走代理 | `this.auditMethod()` 不会异步（也不走事务） | 写入方法放在**另一个 Bean**（`AsyncAuditLogRecorder`），由切面通过接口调用 |
| ThreadLocal 不跨线程 | `SecurityContextHolder` / `RequestContextHolder` 都是 ThreadLocal，异步线程里取到 `null` | 切面在**请求线程里**先把用户/IP/UA/时间取出来，装进 `AuditEvent` 再传参 |
| ThreadLocal 在线程池里残留 | 业务方法写入的"运行时补充说明"（`AuditTrace`）若不清理，会串味到下一条审计 | 切面 `finally` 里无条件 `AuditTrace.clear()` |

**异步的直接证据**（本机实测，日志原文）：

```
DEBUG --- [hr-security] [        audit-1] c.h.audit.AsyncAuditLogRecorder : 审计异步写入：operation=查看员工敏感信息, thread=audit-1
```

写入线程是 `audit-1` 而不是 `http-nio-8080-exec-*`，说明确实离开了请求线程
（这也是"`@Async` 没生效"时最快的排查手段：看写入线程名）。

### 4.4 运行时细节怎么进审计

注解只能写静态文案，但审计常常要记**运行时的具体情况**（"状态改为禁用(0)"、
"migrated=3"、"keyId k1 → k2"）。做法是业务方法内调 `AuditTrace.append("…")`，
切面落库时 `drain()` 取出并拼接，最后 `clear()`。这样 detail 里就有了可读的业务上下文，
而敏感值仍然一个字都不写。

### 4.5 目标 id 从哪来

- 优先取注解指定的入参（`targetIdArgIndex = 0`，如 `getSensitive(Long id)`、`updateStatus(Long id, …)`）；
- 入参不是 id 时（如 `create(EmployeeDTO)`）**退而从返回值里反射取 `getId()`**——
  这样"新增员工"也能记下新记录的 id，而不必为了埋点改业务方法签名。

## 5. 客户端 IP 与代理链

`request.getRemoteAddr()` 在 Nginx / 网关 / 负载均衡后面拿到的是**网关自己的 IP**
（所有记录看起来都来自同一个地址，审计价值归零）。真实客户端 IP 由代理写入
`X-Forwarded-For`，格式是逗号分隔链：

```
X-Forwarded-For: 真实客户端, 代理1, 代理2
```

取**最左**一个（`IpUtils.clientIp`）。安全提醒：该头可被客户端伪造，
只有在"可信代理会覆盖它"的前提下才可信（生产应在最外层 Nginx 重置该头，应用只信任内网网关）；
审计里记它是为了留线索，不作为鉴权依据。测试用例 A6~A8 用
`X-Forwarded-For: 203.0.113.9, 10.0.0.1` 断言记录的是 `203.0.113.9` 而不是网关地址。

## 6. 埋点清单（红线 + 可选项）

| 位置 | operation | 理由 |
|---|---|---|
| `EmployeeServiceImpl#getSensitive` | 查看员工敏感信息 | **最重要的一条**：明文唯一出口 |
| `EmployeeServiceImpl#update` | 修改员工 | 敏感字段被谁改了要单独能查（detail 记改了哪几个字段名） |
| `EmployeeServiceImpl#create` / `#delete` | 新增员工 / 删除员工（离职） | 档案变更与离职 |
| `DeptServiceImpl#create/#update/#delete` | 新增/修改/删除部门 | 组织结构是数据权限的维度 |
| `CryptoMigrationServiceImpl#backfill` | 历史数据加密迁移 | 数据级运维动作，detail 带执行报告 |
| `UserServiceImpl#updateStatus` | 变更账号状态 | 权限变更本身是审计对象 |
| `UserServiceImpl#assignRoles` | 分配用户角色 | 提权最需要留痕 |
| `DataKeyServiceImpl#rotate/#reencrypt/#disable` | 轮换/重加密/停用密钥 | 密钥生命周期变更史 |
| `AuditLogServiceImpl#page` | 查询审计日志 | **翻账也要留痕**，避免"内鬼先翻一遍"成为盲区 |

## 7. 已知演进方向（答辩可讲，本周不做）

1. **审计表膨胀**：按时间分区（MySQL 8 支持 `PARTITION BY RANGE`）、冷热分离、
   定期归档到对象存储；管理端只查最近 N 天。
2. **防篡改**：现在是"应用不提供改接口"，更强的做法是每行算 HMAC 链式哈希（类似区块链思路），
   或写入 append-only 的独立审计库/日志服务（ELK、Splunk）。
3. **越权尝试留痕**：接入 Spring Security 的 `AuthorizationDeniedEvent`，
   把 403 也记成 `FAILURE`，补上第 3.2 节说的覆盖缺口。
4. **告警**：对"同一账号短时间内大量查看明文""非工作时间查看敏感信息"等模式做实时告警——
   审计的真正价值在于**被动记录变成主动发现**。
5. **异步可靠投递**：现在是内存线程池（进程崩溃会丢少量审计），生产可换成
   本地消息表 + MQ，做到"至少一次投递"。
