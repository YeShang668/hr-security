## BUG8-1（重要）测试脚本用 `curl -d` 内联中文 → 后端 500，把越权用例和注册用例一起判成"失败"

**现象**：新写的 `security-e2e-test.sh` 首跑 50/52，两条失败且都是 500：
- `H1 EMPLOYEE 改他人员工档案 → 403`，实际拿到 `500`；
- `B10 注册合规口令 → 200/409`，实际拿到 `500`。

**定位依据**（关键是没把它当"权限没生效"）：
- H1 走的是 `PUT /api/employees/1`，同一 token 在 `V11 POST /api/employees` 上是正常 403 —— 说明权限链没问题；
- 两条失败用例的共同点不是"权限"，而是**请求体里带中文**（`"name":"改别人档案"`、`"nickname":"合规口令探针"`），
  而所有通过的用例请求体都是纯 ASCII；
- 于是怀疑编码：Git Bash 里 `-d '{"name":"中文"}'` 会把内联中文按 **GBK 字节**发出去。

**根因**：服务端按 UTF-8 解析 JSON，收到 GBK 字节 → Jackson 抛 `HttpMessageNotReadableException`
→ 落到 `GlobalExceptionHandler` 的 `Exception` 兜底 → 500。
**这不是权限问题，也不是校验问题，是测试脚手架的问题**——而且这个坑第 5 周已经踩过（`BUG5-4` 家族：
"Git Bash 内联中文变 GBK，请求体写 UTF-8 文件再 `--data-binary @file`"），只是新脚本又犯了。

**修复**：脚本内统一改用 python 写 UTF-8 临时文件再发送（与 `e2e-test.sh` / `audit-e2e-test.sh` 同一写法）：

```bash
send_json() { $PY - "$1" "$2" "$3" <<'EOF'
...tempfile('w', encoding='utf-8')... subprocess.run(['curl','--data-binary','@'+path])...
EOF
}
```
H1 改成 `put_json`、B7~B10 改成 `post_anon_json`，两条用例随即通过（50/52 → 52/52）。

**教训**：
1. **看到 500 先排除"请求本身是不是合法"**，再怀疑业务逻辑；否则会把脚手架问题误诊成安全缺陷（方向完全错）。
2. 凡是"新写一个测试脚本"，第一件事是照抄已有脚本的 `send_json` 写法，不要图省事用 `-d` 内联中文。

**连带发现（记在观察里，不是本 Bug 的修复范围）**：请求体反序列化发生在**授权检查之前**，
所以"未授权 + 非法 body"返回 500 而不是 403。这意味着未认证用户可以靠构造坏 body 探测内部错误
（本项目兜底异常不泄露堆栈，只回统一文案，风险可控），但**行为不一致本身**值得记一笔：
如果将来要在入口做更严的访问控制，得考虑把鉴权提前到 body 解析之前（例如用过滤器做粗粒度拦截）。

## BUG8-2 `gen-cert.sh` 里 `-subj "/C=CN/..."` 被 Git Bash 改写，openssl 直接报错

**现象**：`bash docker-build/nginx/gen-cert.sh` 失败：

```
req: subject name is expected to be in the format /type0=value0/type1=value1/...
This name is not in that format: 'C:/Program Files/Git/C=CN/ST=Chongqing/...'
```

**根因**：MSYS2（Git Bash）会把"看起来像路径"的命令行参数自动转换成 Windows 路径。
`-subj` 的值以 `/` 开头，正好被当成 POSIX 路径 → 变成 `C:/Program Files/Git/C=CN/...`。
这在 Linux/CI 上不会出现，是**纯 Windows 开发环境的坑**。

**修复**：关闭这一个进程的参数转换（只排除出问题的那个参数值）：

```bash
MSYS2_ARG_CONV_EXCL='/C=CN' openssl req -x509 ... -subj "/C=CN/ST=.../CN=localhost" ...
```

**教训**：写"只在 Windows 上跑、但要在 CI 上也能跑"的脚本时，凡是传给原生 Windows 程序的
**非路径参数**（`-subj`、`-Dxxx=yyy` 这类），都要意识到 MSYS 可能改写它。

## BUG8-3 修 BUG8-2 时"排除过头"，反而让 openssl 写不出文件

**现象**：把修复写成 `MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*' openssl ...` 之后，
错误从"subject 格式不对"变成：

```
req: Can't open "/c/Users/.../certs/server.key" for writing, No such file or directory
```

**根因**：`'*'` 表示**所有**参数都不做转换，于是 `-keyout /c/Users/...` 的 POSIX 路径原样传给
**原生 Windows 版 openssl**，它不认识 `/c/Users/...`（那是 MSYS 的挂载路径），自然写不出文件。

**修复**：把排除范围收窄到"只有那一个出问题的参数"（前缀匹配）：
`MSYS2_ARG_CONV_EXCL='/C=CN'`。`-keyout` / `-out` 继续享受正常的路径转换。

**教训**：**排除/绕过要最小化**。上一版是"全部关掉"看起来最省事，实际把"路径要转换"这个
隐含正确行为也一起关掉了——修 bug 修出新 bug，通常就发生在"用力过猛"的那一步。
两轮修复合并成一行注释写进脚本，避免下一个人再试一次 `'*'`。

## BUG8-4 压测脚本假设审计表有 `elapsed_ms` 列，查询报错被静默吞掉

**现象**：压测脚本输出 `审计记录的方法平均耗时=None`。看起来像"没数据"，但审计行明明有 800 条。

**定位依据**：手工执行脚本里那条 SQL：

```
ERROR 1054 (42S22): Unknown column 'elapsed_ms' in 'field list'
```

**根因**：`AuditEvent` 里有 `elapsedMs` 字段，但 `sys_audit_log` **没有对应列**——
它只被拼进 `detail` 文本（"…；耗时 0.9ms"）。而脚本里的 `sql_one()` 只取 stdout 的最后一行，
mysql 的错误走 stderr，于是**查询失败被静默吞成 `None`**，表现成"没数据"。

**修复**：改为从 `detail` 文本里正则解析（`耗时 (\d+)ms`），并对 800 条样本做聚合
（avg 0.9ms / P95 2ms / max 4ms）；同时在文档里记下**正确的下一步**：
把方法耗时提升为独立数值列，未来才能直接做耗时聚合与慢操作排行。

**教训**（两条，都属于"测试框架自己要有断言"的族谱）：
1. **辅助函数不要把失败伪装成空值**：`sql_one()` 这类函数要么显式区分"查询失败"和"查不到"，
   要么在 stderr 非空时报错。本周它把一个 SQL 语法错误变成了一个看起来正常的 `None`。
2. **"字段存在"本身要验证**：写测试代码时假设了 schema，而 schema 是别人的事实。

## BUG8-5 用例断言"恰好 1 条"，脚本重跑就假失败

**现象**：`security-e2e-test.sh` 第二次运行时 `X5 部门列表原样返回该名称` 失败：期望 1，实际 2。

**根因**：X 组的 XSS 用例会创建一个固定名字的探针部门，而**部门名没有唯一约束**，
脚本重跑就再建一个同名部门；断言写的是"恰好 1 条"（`== 1`），第二次自然变成 2。
这不是产品缺陷，是**断言把"数据事实"当成了"功能契约"**。

**修复**：断言改为"至少 1 条"（`>= 1`），并在用例名后面输出实际条数；
同时把"重跑会累积探针数据"这件事写进脚本头部注释（与其它脚本一致：同一数据卷不可原样重跑）。

**教训**：断言要写"被保护的性质"（"这个名称能被原样读出"），而不是"当前环境的偶然计数"。
凡是**没有唯一约束**的实体，断言计数就只能用"至少/包含"，不能用"等于"。

## 观察（不修，但要记住）

1. **本机 Docker 起不来 + Git Bash 的 curl 是 Schannel 后端**：
   `CURL_CA_BUNDLE` 和 `--cacert` 都**不生效**（Schannel 只认 Windows 证书库）。
   这直接决定了本周的取舍：228 条功能用例继续走 http（`docker-compose.test.yml` 临时映射端口，
   保持严格性），TLS 入口单独 12 条专项用例（内部显式 `-k`）。
   → 推论：**不要给全量回归加 `-k`**，那等于让 228 条用例同时失去证书校验能力。
2. **口令策略只在入口卡，等于内部留后门**：注册加了强度校验，但种子 `admin` 的密文还是弱口令
   ——"策略只覆盖了最容易被检查的那个入口"。所以本周把演示口令从 `123456` 换成 `Hr@123456`
   （含两个 `init.sql` 里的 BCrypt 密文重算），并把全部 fixture / 文档 / 前端提示一起改掉。
   → 生产里同类问题的形态是"改密/重置/管理员建号/第三方登录"各写一套规则。
3. **参数化 ≠ 值语义安全**：`#{}` 拦住了"改写 SQL 结构"，但 `%`/`_` 是 LIKE 的**值语义**，
   参数化拦不住（`keyword=%` 命中全表）。要修的是"值怎么理解"，不是"值怎么拼"。
4. **限流必须在密码校验之前**：放在后面的话，锁定期的正确密码照样能登录，锁等于没锁。
   另外账号维度（5）严于 IP 维度（20）是刻意的：IP 维度卡太死会变成"帮攻击者锁别人账号"的 DoS。
5. **nginx `add_header` 的继承陷阱**：`location` 里一旦出现 `add_header`，就不再有 server 级的其它
   `add_header`。所以 `hr.conf` 里**没有**给 `/assets/` 单独加 `Cache-Control` ——
   想要缓存又要安全头，就得在多个位置重复写或抽 `include`（本周选择先保证安全头在场）。
6. **审计是异步的 → 一致性校验必须轮询等落库**：第 7 周的 `wait_sql` 思路在压测脚本里同样适用
   （`--check-audit` 用轮询 30s 的方式比对行数），"发完就查"一定会误判。
7. **越权矩阵必须有对照组**：只断言"EMPLOYEE 被拒"会掩盖"接口整体挂了"（全 403 看起来最安全）。
   所以 V13/V14 专门断言"该允许的确实允许"。
8. **第 7 周的"用例数校验"本周继续生效**：新增的两个脚本（52 / 12 条）都纳入了逐脚本用例数核对，
   所以"用例被静默跳过"这类问题不会再以"全绿"的形式蒙混过关。
