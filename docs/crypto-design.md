# 敏感字段加密与动态脱敏设计（第 6 周）

> 本文件是毕设论文"设计"章节的**话术底稿**：按「场景 → 风险 → 策略 → 实现 → 取舍」组织，
> 与第 4 周的《scene-risk-strategy.md》同一套框架，答辩与面试可直接照这个顺序讲。
> 对应代码：`com.hrsecurity.crypto.*`、`EmployeeServiceImpl`、`sql/init.sql`。

## 1. 场景与风险（为什么必须字段级加密）

人事系统里最敏感的数据不是"业务数据"而是**自然人身份信息**：身份证号、手机号、银行卡、工资。
本系统面对的实际风险有三类：

| 风险 | 场景 | 只做"传输加密/口令保护"为什么不够 |
|---|---|---|
| 拖库 | SQL 注入、备份文件泄露、运维/外包直接查表 | 表里是明文，拿到库 = 拿到全部敏感信息 |
| 越权访问 | 普通员工调接口查同事工资 | 只在前端隐藏不够，必须在后端按权限脱敏 |
| 内部滥用 | 管理员批量导出敏感字段 | 没有任何访问痕迹，事后无法追责 |

结论：**存储层要密文（拖库也读不出），访问层要脱敏（有权也不默认给全量），行为层要审计（下周做）**。
本周落地前两条，第三条留切面位置。

## 2. 算法与参数选择（答辩必答）

- **算法**：AES-256-GCM，用 JDK 自带 `javax.crypto`（`Cipher.getInstance("AES/GCM/NoPadding")`）。
  毕设红线是"不自己实现密码算法"，同时也不引入第三方加密库——JDK 自带实现经过长期检验，
  也避免了第三方库版本/补丁带来的供应链风险。
- **密钥长度 256 位（32 字节）**：AES 支持 128/192/256，取上限；密钥由环境变量注入，不进代码库。
- **IV 12 字节（96 位）随机，每次加密重新生成**：这是 GCM 最关键的一条。
  GCM 中同一密钥下 **IV 复用会导致灾难性后果**：两个明文异或关系泄露、认证密钥可被恢复从而伪造密文。
  所以实现里每次 `encrypt()` 都 `SecureRandom.nextBytes(iv)`，绝不复用，也绝不把 IV 固定在配置里。
- **认证标签 128 位**：GCM 支持的最长标签，抗伪造能力最强。标签随密文一起存储，
  解密时由 `GCMParameterSpec(128, iv)` 校验，**改一位密文就解不开**（见第 6 节 C5 用例）。
- **为什么选 GCM 而不是 CBC**：CBC 只提供机密性，不提供完整性，必须再叠加 HMAC 才安全（Encrypt-then-MAC），
  实现复杂且容易出错（padding oracle 攻击就是 CBC 的经典坑）；GCM 是 AEAD，一次做完两件事。
- **为什么不用非对称加密**：字段数据量大、加解密频繁，RSA 既慢又有长度限制。
  非对称更适合"保护对称密钥"（下周 KEK/DEK 里的 KEK 思路）。

## 3. 密文格式（自描述，为演进留口子）

```
v1:{keyId}:{ivBase64}:{cipherBase64}
例：v1:k1:KvOvBkZbCNWM2xga:KZFKgu5/f8YuEPIlo4KghlRNAkMWWoKaEY7l
```

- `v1`：**格式版本号**。将来换算法（如国密 SM4）或改格式，老数据仍能按 v1 解，新数据写 v2，平滑迁移。
- `keyId`：**密钥版本号**。密钥轮换时新数据用 `k2` 加密，老密文按 `k1` 取老密钥解密，
  这是"轮换不中断服务"的前提（下周 KEK/DEK 直接复用这个字段）。
- `iv` + `cipher`：IV 不必保密但必须唯一，与密文同存即可。

存储列统一 `VARCHAR(512)`：18 位身份证密文 Base64 后约 100 字符，留足余量。

**格式非法的处理**：`decrypt()` 遇到不以 `v1:` 开头的值直接抛异常，不"当明文返回"。
理由：如果某行历史数据漏迁移，静默当明文会让人以为系统已经全加密，属于最危险的假安全感。

## 4. 加密与业务代码解耦（MyBatis-Plus TypeHandler）

```java
@TableField(value = "id_card_enc", typeHandler = AesTypeHandler.class)
private String idCardEnc;   // 内存里是明文，数据库里是 v1:k1:... 密文
```

`AesTypeHandler extends BaseTypeHandler<String>`：写入前加密、读取后解密。

**为什么用 TypeHandler 而不是在 Service 里手动加解密**（面试高频）：

1. **不遗漏**：只要走这个实体的读写都会被处理，不依赖开发者记得调用（漏一处就是明文落库事故）；
2. **不重复**：加解密规则只有一处实现，换密钥/换算法不用翻遍 Service；
3. **语义清晰**：实体字段就是"明文字段"，加密只是存储细节，业务代码读到的永远是明文。

代价：**无法在 SQL 层对密文列做模糊查询**（`like` 匹配不到任何东西），所以需要 `id_card_hash`。

**踩过的坑（BUG6-1）**：`@TableName(autoResultMap = true)` 必须加。
MyBatis-Plus 默认的实体结果映射**不带**自定义 TypeHandler，只在写入方向生效；
漏加的典型表现是"写进去是密文、读出来还是密文"，业务层拿到一长串 `v1:k1:...` 还以为是数据问题。

## 5. 可检索性设计（加密之后怎么按身份证查人）

加密带来的现实问题：**密文是随机化的，等值查询和唯一约束都失效**。
本系统的做法是"**密文存储 + 盲索引检索**"，两者分工明确：

| 用途 | 列 | 算法 | 特点 |
|---|---|---|---|
| 还原明文 | `id_card_enc` | AES-256-GCM（随机 IV） | 可逆，同一明文两次密文不同 |
| 精确检索 / 唯一校验 | `id_card_hash` | **HMAC-SHA256(身份证)**，64 位 hex | 单向不可逆，同一身份证哈希稳定 |

- **为什么用 HMAC-SHA256 而不是裸 SHA-256**：身份证号空间有限（地区码 + 生日 + 顺序码），
  裸哈希可被彩虹表/暴力枚举反推，等于没加密。加一个密钥（盐）后，攻击者即使拿到库也造不出表——
  除非同时拿到密钥。这就是"盲索引"（blind index）的思路。
- **哈希密钥从哪来**：环境变量 `ID_HASH_SALT` 优先；未配置时由 AES 主密钥做**域分隔派生**
  （`SHA-256("hr-security:id-card-hash:v1" ‖ 主密钥)`）。同一主密钥派生不同用途的子密钥时必须带不同标签，
  避免加密密钥与哈希密钥直接共用。
- **落地**：`GET /api/employees/search?idCard=xxx` 全程不解密、不扫全表（哈希列有唯一索引）；
  身份证唯一校验也走同一列——`UNIQUE KEY uk_emp_id_card_hash`，业务层查不到重复才插入。
- **注意**：盐或主密钥一旦变更，历史哈希全部失效，需要重建索引列（写进运维注意事项）。

## 6. 动态脱敏（默认脱敏，明文是显式动作）

脱敏是"给不同人看不同精度"，规则参考 GB/T 35273《个人信息安全规范》与行业惯例：

| 字段 | 规则 | 示例 |
|---|---|---|
| 身份证 | 保留前 3 后 4 | `110***********1234` |
| 手机号 | 保留前 3 后 4 | `138****0001` |
| 银行卡 | 仅保留后 4 位 | `***************3445` |
| 工资 | 全部掩码 | `****` |

三条设计决策，答辩要能讲出理由：

1. **脱敏在后端做**。前端脱敏等于没脱敏——接口返回了明文，抓包或改 JS 就能看到。
   实现集中在 `Service#toVO`，不散落在 Controller，避免新加接口忘了脱敏。
2. **列表/详情对所有人一律脱敏，连 ADMIN 也一样**（最小披露）。明文只从
   `GET /api/employees/{id}/sensitive` 这一个出口出，且要求独立权限 `employee:sensitive:read`。
   好处：明文访问永远是一次**显式行为**，审计只需盯一处；列表接口即使被越权读取，泄露面也只有脱敏值。
3. **权限用权限编码而不是角色名**：`employee:sensitive:read` 由角色绑定（种子数据里仅 ADMIN 拥有），
   以后要给"HR 专员"开这个权限只需加一条角色-权限关系，不用改代码。权限编码同样进 Redis 缓存
   （`user:perms:{userId}`），角色/权限变更后与角色缓存一起删，**即时生效、无需重登**。

**防"掩码写回"**（脱敏系统最常见的坑）：列表返回 `138****0001`，如果前端把脱敏值回填表单再提交，
就会把掩码当新明文加密写库，真实号码被覆盖丢失。本系统前后端各设一道防线：

- 前端：编辑弹窗**不回填**敏感字段，留空即"不修改"（占位提示写明）；
- 后端：DTO 校验用格式正则拦截（`139****2222` 不符合手机号格式 → 400），
  且 Service 里"字段为空就不覆盖"，即使前端漏做也不会写坏数据。

## 7. 历史数据加密迁移（幂等刷数）

真实项目里"新写入加密"只解决一半问题，存量明文数据必须刷。做法（`POST /api/admin/crypto/backfill`，仅 ADMIN）：

1. 读"旧系统明文表" `legacy_employee_plain`（本项目用一张模拟表/演示数据源，
   真实场景是老系统表、CSV 导出或备份文件）；
2. 按 `emp_no` 找到员工记录；
3. 明文写进实体的敏感字段（走同一套 TypeHandler 加密），同时刷新 `id_card_hash`；
4. 返回执行报告：`scanned / migrated / skipped / unmatched`。

**幂等怎么保证**：判断依据是"目标记录是否已有敏感数据"，有就跳过。
**不能用"密文是否相同"判断**——每次加密 IV 随机，同一明文两次密文必然不同。

**为什么迁移不写一段 SQL 脚本**：脚本会复制一份加密逻辑，一旦程序与脚本的算法/keyId/哈希不一致，
就会出现"一半数据解不开"的事故。让迁移复用应用侧同一套代码，是唯一不会漂移的做法。

**明文源的处理**：迁移完成后应 `DROP TABLE legacy_employee_plain`（或清空），
否则"旧表还是明文"，加密白做。这一步是运维动作，写在 README 与本节里。

## 8. 密钥管理现状与下周计划

**本周（第 6 周）**：

- `KeyProvider` 接口 + `EnvKeyProvider` 实现：密钥来自环境变量 `AES_MASTER_KEY`（32 字节 Base64），
  其次本地未提交的 `application-local.yml`；**两处都缺则启动失败**（fail fast）。
  密钥绝不入库、绝不进 git；日志只打印主密钥指纹（SHA-256 前 8 位）便于确认"换没换密钥"。
- `keyId` 已写进密文，轮换的口子已经留好。

**为什么必须 fail fast**：密钥一旦有"默认值"，就一定会有人带着默认密钥上线，
这等价于库里所有密文可解——比不加密更危险（有种虚假的安全感）。

**下周（第 7 周）**：KEK/DEK 两级密钥
——DEK 密文存库、由环境变量里的 KEK 解密得到，实现"密钥本身也不落明文"；
再加密钥轮换（新数据用 k2、老数据按 keyId 用 k1 解，后台批量重加密）。
届时只需换 `KeyProvider` 的实现，`AesGcmCipher`、TypeHandler、业务代码**一行都不改**——
这就是本周先抽接口的原因。

## 9. 已知取舍与边界（诚实记录，面试官喜欢听）

| 取舍 | 现状 | 说明 |
|---|---|---|
| 密文损坏的表现 | **读整行失败**（fail loud，返回 500，日志有"完整性校验失败"） | 不静默降级返回乱码/null，避免掩盖密钥错配或数据被篡改；代价是该行修复前无法通过接口读取，需运维清掉坏密文后重录 |
| 单行坏数据影响面 | 该行所在的列表查询整体失败 | 生产可考虑"按行降级 + 告警 + 修复队列"；毕设演示选择"宁可报错也不给错数据" |
| 密钥轮换 | 未做（下周） | 密文已带 keyId，轮换无需改格式 |
| 加密字段的模糊查询 | 不支持（只能精确查） | 通用替代方案是分词索引/网关级加密搜索，超出毕设范围，写入文档作为权衡 |
| 迁移触发方式 | ADMIN 接口触发 | 生产更推荐独立一次性 Job/CLI（不进 Web 层）；本项目为便于演示与自动化回归放在 ADMIN 接口，并保证"仅管理员 + 幂等 + 有执行报告"三条 |
| 前端明文缓存 | 弹窗关闭即丢弃，不写本地存储 | 明文不落 localStorage，减少泄露面 |
| HTTPS | 未启用（10 月做） | 当前明文只在网络传输中出现于"提交表单"和"查看完整信息"两个请求，HTTPS 前部署属于必要加固 |
| 审计明细 | 未落库（下周 AOP） | 位置已留：`getSensitive()` 是明文唯一出口，切面挂这里即可 |
